# SOLUTION

`result.json` — ответ `daily-totals` для `c_7` за 27–31.03, получен по порядку из `TASK.md`
(`scripts/verify/run-pipeline.sh`). Он совпадает до копейки с независимым эталоном, посчитанным по сырым
данным внешнего API без кода сервиса (см. «Как проверял»).

## Что сделано

**Скидки.** Миграция `002_discounts.sql` (`discount_percent NUMERIC(5,2)`, `paid_kop BIGINT`).
`daily-totals` отдаёт `{ date, total, gross, discount, net }`: всё считается в копейках, `discount = gross - net`
— тоже в копейках, в рубли переводится только ответ.

- `discountPercent` и `amountPaid` принимаются числом или строкой. Если полей нет — это старый заказ: скидка 0,
  `net = gross`. Если есть скидка, но нет `amountPaid`, `net` считается целочисленно (`applyDiscount`).
- Невалидный заказ (400 у вебхука, `invalid` в статистике синка): `amountPaid` больше `amount`, скидка вне
  0..100 или точнее сотых, строка-не-число, сумма больше 1 трлн ₽. Строки разбираются строго: прежний
  `Number("")` дал бы для `amountPaid: ""` молчаливую скидку 100%, а огромная сумма переполняла `BIGINT` и
  обрывала весь `/sync` ошибкой БД.
- **Выкатка на существующую БД.** У сохранённых ранее строк скидка неизвестна (`paid_kop = NULL`), а обычный
  `/sync` счёл бы их `stale` — версия та же. Поэтому строку с `paid_kop IS NULL` перезаписывает и та же
  версия: после выкатки достаточно одного `POST /sync`. До него такие строки считаются без скидки.

**Жалоба по c_7** — три ошибки, а не одна:

| # | Ошибка | Что ломала у c_7 |
|---|---|---|
| 1 | День заказа считался по смещению таймзоны **на сегодня**, а не на момент заказа | 29, 30, 31.03 |
| 2 | Гонка при параллельных вебхуках: новую версию заказа перетирала старая | 27, 29, 31.03 |
| 3 | `toKop` терял копейку на погрешности double (`4723.9 * 100 = 472389.99999999994`) | `net`: 98 заказов в данных, 65 из них оплачены |

## Причина расхождения и как нашёл

Снял поведение исходного кода по порядку из `TASK.md` и параллельно собрал сырые данные: все страницы
`/orders` и все вебхуки, перехваченные своим приёмником. По ним независимо посчитал эталон
(`scripts/verify/reference.py`: Python, `zoneinfo`, `Decimal`, итоговая версия заказа — с максимальным
`updatedAt`). Исходный код расходился с эталоном ровно 29–31.03.

**1. Летнее время.** `c_7` — `Europe/Berlin`, где 29.03.2026 в 01:00 UTC часы переводят с UTC+1 на UTC+2.
`TotalsService` брал `tzOffsetMinutes(timezone, new Date())` — смещение на момент запроса (сейчас +1) —
и применял его ко всем заказам, поэтому заказы после перевода часов с 22:00 до 23:00 UTC уходили в
предыдущий день. Отчёт ещё и зависел от того, *когда* его запросили: летом сломались бы дни до 29.03.
Исправление: `dateInTimeZone(createdAt, timezone)` через `Intl.DateTimeFormat`.

**2. Гонка в вебхуках.** После исправления 1 эталон всё ещё не сходился по 27, 29 и 31.03. Сверил итоговое
состояние каждого заказа в БД с эталоном: у `o_02083`, `o_02281`, `o_02455` лежала не последняя версия
(у `o_02281` — `paid` от 03:50, хотя пришёл и `refunded` от 04:50). Вебхуки приходят пачками параллельно,
а `apply` делал «прочитать → сравнить `updatedAt` → записать» тремя шагами: оба запроса видели старую
строку, и выигрывал записавший последним. Исправление: сравнение версий — в самом
`INSERT ... ON CONFLICT DO UPDATE ... WHERE orders.updated_at < excluded.updated_at`, атомарно под
блокировкой строки; результат — из `RETURNING (xmax = 0)`.

**3. Копейка.** `toKop` и новый `parseKop` режут десятичную запись числа (`String(4723.9)` = `"4723.9"`, строку
из API — как есть), а не умножают в double. Доли копейки по-прежнему отбрасываются. На `total` ошибка не
влияла (у `amount` нет копеек), но сломала бы `net`.

## Как проверял

1. **Тесты:** `npm test` — 46, все проходят; `npm run typecheck` чистый. Новые покрывают: gross/discount/net,
   строковые и отсутствующие поля скидки, скидку без `amountPaid`, строки до миграции и их дозаполнение
   синком, переход на летнее время при «сейчас зима» и «сейчас лето» (`vi.setSystemTime`), параллельную
   доставку версий одного заказа (20 × 5 одновременных запросов), копейку на `4723.9`, валидацию.
2. **Тесты ловят ошибки:** со старыми `tzOffsetMinutes(…, new Date())`, `Math.floor(rub * 100)` и старым
   `apply` соответствующие тесты падают.
3. **Деньги:** `toKop` и `applyDiscount` разово прогнал на 1 млн случайных сумм и скидок против точной
   целочисленной арифметики (BigInt) — 0 расхождений.
4. **Сквозная сверка:** каждый прогон `run-pipeline.sh` (чистая БД, порядок из `TASK.md`) совпал с
   эталоном до копейки; итоговое состояние всех 5030 заказов в БД — тоже, 0 расхождений.

## Что ещё заметил

**Внешний API:**
- у 1177 из 5030 заказов полей скидки нет; `discountPercent` бывает строкой, `amount` — строкой (`"3100.00"`);
- у 288 заказов `createdAt` без зоны — это UTC: в синке и вебхуках строки совпадают, контракт тот же;
- вебхуки приходят с повторами (92 доставки на 21 заказ), не по порядку и параллельно; у заказа бывает несколько версий с разной скидкой — верна последняя по `updatedAt`.

**Код:**
- таймзона клиента кешируется навсегда — нужен TTL по `fetched_at`;
- `POST /sync` синхронный (~16 с на 52 страницы) и при ошибке начинает с начала — за прокси упрётся в таймаут;
- `tzOffsetMinutes`/`dateAtOffset` в `src` больше не используются, но покрыты тестами — оставил с пометкой.

## Допущения

- `total = gross`, как в задании. День заказа — по `createdAt` в таймзоне клиента, как было: остальные дни, по жалобе, сходятся.
- `net` — это `amountPaid` из API, ему доверяем (с `discountPercent` не сверяем). Без `amountPaid`: `amount × (100 − d) / 100`, доли копейки отбрасываются — соглашение проекта «не досчитываем клиенту».
- `refunded` в отчёт не входят, как и раньше.
- Две версии с одинаковым `updatedAt` неразличимы — остаётся записанная первой. В данных таких пар нет; если они возможны, нужен монотонный `version` в API.
- Три существующих теста `totals.test.ts` сравнивали ответ целиком по старому формату `{ date, total }`. Формат меняет само задание, поэтому в ожидания добавлены `gross/discount/net`; значения `total` не тронуты.
